# 0007. Несколько источников цен через провайдеры

> Обновлено: 2026-08-21

## Статус

Принято

## Контекст

Одной площадки мало: пока и закупка, и продажа берутся с FunPay, маржа показывает арбитраж
внутри одной площадки. Настоящие связки появляются, когда источников несколько.
Проверка показала, что площадки отдают данные принципиально по-разному.

## Решение

Синхронизация разделена на общую часть и провайдеры источников.

Общее (`components/sources/`): группировка предложений в варианты, срез рыночных цен,
сохранение карточек продавцов и их предложений, пересчёт статистики, история цен, аудит.
Провайдер отвечает ровно за два действия: отдать каталог и разобрать раздел в список предложений.

Подключены три источника:

| Источник | Как получаем | Особенности |
|---|---|---|
| FunPay | Разбор публичных HTML-страниц | Раздел отдаётся целиком, есть фильтры лота |
| Digiseller | Официальный публичный API `api.digiseller.com` | Каталог по магазинам: продавец → категории → товары |
| Playerok | Их собственный GraphQL | Не больше 24 позиций за запрос, ограничение частоты |

## Альтернативы

- Отдельный сервис синхронизации на каждую площадку. Отклонено: три копии одной логики
  записи в базу, расхождения появятся на первой же правке.
- Сохранённые запросы (persisted queries) для Playerok. Отклонено: их хеши меняются с каждой
  сборкой сайта; полный текст запроса стабильнее.
- Headless-браузер для Playerok. Отклонено: их GraphQL отвечает обычному HTTP-клиенту.

## Последствия

- Новая площадка — это файл провайдера, строка в реестре и запись в справочнике `marketplaces`.
- Playerok отдаёт раздел частями: за один проход читается около тысячи позиций из десятков тысяч.
  Это честно помечается в предпросмотре и в ответе синхронизации, статистика считается
  по прочитанной части.
- Digiseller устроен по магазинам, поэтому «раздел» там — категория конкретного продавца,
  и администратор указывает его ID.
